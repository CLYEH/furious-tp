## 2. 量測方法

### 2.1 共用同一套幾何程式

A 與 B **走完全相同的 union / clip / hole 程式碼**([`ground-probe.py`](ground-probe.py) 的 `coverage`、`holes`、`class_areas`、`edge_band`)。若兩邊各用各的幾何邏輯,比較出來的會是兩支 script 的差異而不是兩份資料的差異。

量測 CRS 一律 **EPSG:3826**(公尺),bbox 由 `contracts/constants/m1_area.json` 讀入,**不另存一份**(與 `etl/osm/bbox.py::from_area_file` 同一個來源)。

### 2.2 兩種獨立方法的對帳

headline 覆蓋率同時用**精確聯集**(shapely `unary_union` → `intersection` → `area`)與**網格取樣**(5 m 間距、cell 中心、490,000 個取樣點)量,兩者失敗方式不同,所以一致才有證據力。

| 資料源 | 精確聯集 | 網格取樣(5 m,490,000 點) | 差 |
|---|---|---|---|
| B(OSM) | 0.554774 | 0.554743 | **−3.1 × 10⁻⁵** |
| A(細計圖) | 0.777727 | 0.777712 | **−1.5 × 10⁻⁵** |

(probe 另外獨立輸出一個 `delta_vs_exact` 欄位,其值為 −1.4 × 10⁻⁵;差異來自它對差值自行四捨五入,而非上表兩個 6 位小數相減。以表內兩欄相減為準。)

再加一層:**同一份 OSM 輸入在兩個不同的 shapely 版本上跑出逐位元相同的結果**(venv shapely 2.1.2 與 anaconda shapely 2.1.1,皆為 `covered_m2 = 6795975.6`、`fraction = 0.554774`、9 個洞且面積清單完全相同)。這排除「數字是某個函式庫版本的產物」。

### 2.3 零值對照組

**本報告出現的每一個 0,都附一個用同一支函式、同一條路徑會回報非零的對照組。** 沒有對照組時,「0 個洞」跟「查詢寫錯了」長得一模一樣。

| 回報 0 的量測 | 對照組(必須非零) | 結果 |
|---|---|---|
| A 的 `holes` 在未排除範圍框時 = 0 | 排除範圍框後同一函式 = 2 個洞、2,722,819 m² | 對照組非零 ✓ |
| `skipped = 0`(兩個資料源皆然) | 考卷 `test_degenerate_rings_are_skipped_and_counted`:3 點環 → `skipped = 1` | 對照組非零 ✓ |
| 完全在 bbox 外的 polygon 貢獻 0 | 同一函式對跨界 polygon 回報 2,500 m²(考卷 `test_polygon_crossing_the_edge_counts_only_the_inside`) | 對照組非零 ✓ |
| 邊緣帶覆蓋 0(考卷合成案例) | 同一函式對滿覆蓋輸入回報 1.0 | 對照組非零 ✓ |
| **data.taipei `/api/v1/dataset/search` 回 `count: 0`** | **空查詢、`'a'`、`'公園'`、`'臺北'`、`'交通'`、`'土地'` 全部也回 0** | **對照組也是 0 → 這個端點無條件回 0,不能用它推論任何事**(見 §4.1) |

最後一列是這條紀律當場救到的一次:若沒有對照組,我會寫成「data.taipei 上找不到土地使用分區資料集」——**那是錯的**,資料集存在(§4.2)。

### 2.4 邊界(bbox 邊緣)有沒有空白帶?

**沒有。** 跨界 polygon 被裁切後,內側部分照算(考卷釘住)。但「有沒有算到」不等於「邊緣看起來有沒有變薄」,所以直接量**沿邊 50 m 帶**的覆蓋率與**內部**的覆蓋率:

| 資料源 | 邊緣帶(50 m)覆蓋 | 內部覆蓋 | 差 |
|---|---|---|---|
| B(OSM) | 58.48% | 55.30% | **+3.18 pp**(邊緣比內部更滿) |
| A(細計圖) | 77.63% | 77.78% | **−0.15 pp** |

兩者都沒有邊緣空白帶。B 的邊緣反而更滿,**成因未判定**——bbox 南緣外是象山山區,大面積 `natural=wood` 跨界進來是一個合理的解釋,但我沒有做能分辨其他解釋的量測,所以不下判定。

跨界元素計數:B 有 54 個 polygon 被裁切、62 個完全在外;A 有 123 個被裁切、13,803 個完全在外(A 是全市檔案,所以「在外」的很多)。

### 2.5 不回述上游 body 是被考卷釘住的

probe 的可用性取樣紀錄**只帶** `at` / `status` / `bytes` / `body_class` / `content_type` / `ms`,錯誤樣本只帶 `at` / `status` / `error_class` / `ms`。考卷用 **allow-list 釘住鍵集合**,不是搜尋某個已知字串:

> 早期版本的考卷只檢查「完整 body 沒有出現在輸出裡」,結果一個把 body 前 16 bytes 以 hex 塞進紀錄的 mutant **活了下來**(M13)。前 16 bytes 也是別人的 body。改成 allow-list 後該 mutant 被殺掉。

**exception 只記型別不記訊息**(`error_class = type(exc).__name__`)——訊息可能夾帶 body 內容。這條也有 mutant 證明過會紅(M6)。

### 5.4 能不能共用 FTP-29 的裁切器?**不能**(附數字)

**票上問的是「能不能共用同一套裁切器」,答案是不能,而且理由用面積才看得出來:**

| | feature 數 | 佔元素數 | **各自聯集面積(m²)** | **佔總覆蓋(6,795,976 m²)** |
|---|---|---|---|---|
| way | 1,567 | 90.3% | 2,914,638 | 42.9% |
| **relation** | **169**(**outer 環數**) | **9.7%** | **4,109,932** | **60.5%** |

**relation 只貢獻 169 個 outer 環(佔 feature 數的 9.7%),卻承載 4,109,932 m² —— 總覆蓋面積的 60.5%。**

> **標籤更正**:169 是 `stats["relation_features"] += len(outers)` 累加的 **outer 環數**,不是 relation **元素**數(一個 multipolygon relation 可以有多個 outer 環)。真實的 relation 元素數更少,所以「少數元素承載多數面積」的結論方向不變、甚至更強;但初版把它寫成「元素數」是錯的。

(兩列相加 7,024,570 m² 大於聯集 6,795,976 m²,差 228,594 m²,因為 way 與 relation 的幾何彼此重疊;故上表最後一欄不是一個分割,兩者相加會超過 100%。若改以「way 聯集 + relation 聯集」為分母,relation 佔 **58.51%**。兩種算法我都列出來,因為選哪一個分母會改變數字,而結論在兩種算法下相同。)

而 `scene-pipeline/src/scene_pipeline/etl/osm/read.py` 只走 `osmium.osm.WAY`:

```python
for way in osmium.FileProcessor(str(path), osmium.osm.WAY):
```

→ **直接沿用 `read_extract` 會漏掉六成的地表面積。** 大面積的 landuse(象山林地、河濱、大型公園)在 OSM 裡通常是 multipolygon relation。

第二個不能共用的地方:`etl/osm/bbox.py` 的 `clip_polyline` 是**折線**裁切(Liang-Barsky + 端點吸附),回傳的是 `ClippedRun` 序列。**面的裁切不是折線裁切**——面被 bbox 切開後要重新閉合成環,折線裁切不做這件事。

**可以共用的是 `BBox` 本身**(`from_area_file`、`contains`、min-inclusive/max-exclusive 的邊界歸屬規則),那是契約層的東西,應該共用以免兩處對邊界歸屬的定義漂移。

→ **下游 ETL 票必須寫明:需要新增 relation(multipolygon)讀取與面裁切,不能宣稱沿用 FTP-29。** 這是本 spike 對下游最具體的一條輸入。

## 7. 「沒被蓋到的」到底是什麼 —— 本報告最關鍵、也最需要小心的一節

> **本節經 round-2 大幅更正。初版的 9.73% 已撤回。**
> 初版把未覆蓋區拆成「道路廊帶 / 建物腳印 / 真正的空白」,其中道路廊帶的定義是**全部 highway way 一律外擴 8 m 半寬**。
> **那個 8 m 沒有出處** —— 它是 probe `--road-halfwidth` 的 argparse 預設值,不是任何規格導出的。它也**不分等級**地套到人行道與階梯上。
> 換成有來源的規則後,同一份資料、同一套幾何,B 單獨的「真正空白」從 **9.73% 變成 15.9%–22.6%**。**教訓不是參數選錯,是:一個沒有來源的預設值一旦寫進結論句,就變成一個沒有人知道自己在相信的假設。**

**單看覆蓋率仍然會高估問題** —— 沒被 landuse polygon 蓋到,不代表會露出灰色橢球:道路會被 FTP-33 的路面 mesh 蓋掉,建物腳印會被 NLSC 3D Tiles 蓋掉。**但這個減法有多大,完全取決於「路有多寬」與「NLSC 真的蓋住多少」,而這兩者初版都是猜的。本節現在把兩者都變成量測。**

probe 的 `blank_split` 現在把**每一項都對「空缺」本身取交集**,並額外回報兩者的重疊,所以沒有任何數字依賴哪一次減法先跑(考卷 `test_blank_split_is_order_independent_and_names_the_overlap` 釘住此性質,對應 mutant R7)。

|---|---|
| 空缺(bbox − B 覆蓋) | 5,454,024.4 m² |
| 空缺 ∩ 道路廊帶 | 1,923,806.0 m² |
| 空缺 ∩ 建物腳印 | 1,466,393.2 m² |
| 空缺 ∩ **兩者皆是** | 63,392.9 m² |

### 7.5 建物那一欄:初版用 OSM 代理 NLSC,現在量了 NLSC 本身

> **初版的論證是循環的**:它說「建物腳印會被**已經在畫面上的 NLSC 3D Tiles** 蓋掉」,量的卻是 **OSM building**。兩者不是同一個集合,而這一欄承擔約 8 個百分點。

### 7.6 混合方案 A+B 的邊際效益(改用有依據的規則)

以「實測路面 + 可行駛 @ 3.0 m」計:

- B 真正空白 **17.36%** → A∪B **2.46%**,**多救回 14.9 個百分點**(約 1.83 km²)
- 以最保守的「實測路面」規則計:**22.55% → 6.27%**,**多救回 16.3 個百分點**

**初版低估了 A 的價值。** 初版寫「多救回 8.77 pp」,是因為那個被誇大的廊帶已經先把大部分空缺吸收掉了。**廊帶縮到有依據的大小之後,補洞的效益反而變大。** 這是本輪更正中唯一一項**強化**了原建議的發現 —— 但它同時也讓「B 單獨」這個備案變弱:**15.9%–22.6%** 的地表沒有分類,不是一成。

## 8. 建議:主案 + 備案 + 選它會放棄什麼

**這一題不由 agent 定案。以下是建議,裁決在 owner / RFC。**

> **關於 owner 對 B 的初步偏好:量測支持它,但不是無條件支持 —— 而且 round-2 之後,支持得更有保留。**
> B 的**分類語意**確實比 A 適合著色(`wood`/`park`/`grass` 直接對應外觀;`住3`/`商三特` 要多一層假設),粒度細 7.6 倍,無效幾何比率較低(0.46% vs 0.79%,約 1.7 倍,**不是一個數量級** —— 初版那句比較拿 bbox 內的 B 對上全市的 A,已更正),而且零新資料源。
> **但 B 單獨會留下 15.9%–22.6% 的地表沒有分類**(初版誤寫 9.73%),而 A∪B 能把它壓到 1.7%–6.3%。**廊帶修正之後,補洞的邊際效益從 8.77 pp 變成 14.9–16.3 pp** —— 也就是說,更正**強化**了混合方案,同時**削弱**了「B 單獨」這個備案。

### 主案:**B 為主分類 + A 補洞(皆離線編譯進 tile)**

1. 地表分類以 **OSM landuse/natural/leisure** 為準(粒度細、語意直接對應外觀)。
2. OSM 未覆蓋處,以 **data.taipei 都市計畫「細部計畫圖」** 補(**不要用主要計畫圖**,中位 8,809 m² 一個街廓一個顏色,太粗)。
3. 剩下的 **1.7%–6.3%**(最保守 6.3%)吃一個中性預設色;道路廊帶交給 FTP-33 的路面 mesh。
4. **零執行期外部依賴、純開放資料。**

### 備案:**B 單獨**

同上但不接 A,**15.9%–22.6%** 的地表吃預設色。**適用情境**:若 owner 判斷「多接一個每年更新、CRS 未宣告、環方向不符規範的來源」不值得那 14.9–16.3 pp。**注意這個備案在 round-2 之後明顯變弱** —— 一成的地表吃預設色與五分之一的地表吃預設色,是不同性質的取捨。

### 8.1 選主案(B + A 混合)放棄了什麼

1. **授權變複雜,而且踩到一個 FTP-6 明文未裁定的前提。** 依 [`LICENSING.md`](../../LICENSING.md),把 OSM 資料併進某圖層會使該圖層成為 **ODbL Derivative Database**,share-alike 外溢(FTP-6 對 props/physics 層明文下過這條禁令)。合併後的地表層若視為單一資料庫,**整層落入 ODbL**,連帶把 OGDL v1 來源的內容一起帶進 share-alike 範圍;若想讓兩層各自保有授權,需要依賴 FTP-6 標為「**前提未裁定**」的 Collective Database 定位。**這是本主案最實質的代價,而且它是一個 human 決定,不是工程決定。**
2. **兩種更新節奏**:OSM 持續變動、A 每 1 年。兩者不同步時,補洞的邊界會跟著 OSM 漂移。
3. **A 的 ingestion 風險**:無 `.prj`(CRS 需向提供者確認,本報告只做推定)、99.2% 的 shape 環方向不符 ESRI 規範、CP950 編碼。
4. **語意混用**:同一張畫面上,一部分顏色代表「地表實際是什麼」,另一部分代表「這塊地被規劃成什麼」。**規劃用途可能與現況不符**(規劃為 `住3` 的地可能是工地),混合後**看起來會很有把握地畫錯**。這是我認為最容易被低估的一項。
5. 多一份 4 MB 來源要版本控管與標示。

### 8.2 選備案(B 單獨)放棄了什麼

1. **15.9%–22.6% 的地表(約 1.95–2.76 km²)沒有分類**,只能吃預設色。以 M1 的尺度,那是駕駛會持續看到的一大片,不是零星角落。(**面積為實測;「駕駛會看到」是推論,我沒有渲染過畫面**,見 §9.6。)
2. 放棄 A 對 B 的**交叉佐證**(§4.5 的 `公` vs `park`、`保` vs `wood`)。
3. **OSM 是活資料**:覆蓋率會隨編輯漂移,可能變好也可能變差,而沒有第二個來源兜底。

### 8.3 不採用 C 放棄了什麼

**先講清楚不採用的理由不是什麼:不是我量到它不可靠(48/48 全綠)。** 理由是:

1. **授權未裁定**(§6.3):要把影像烘進我們散布的 tile,目前沒有已確立的授權依據。而**不烘進 tile 就等於接受執行期外部依賴**。
2. **執行期外部依賴的後果不對稱**:FTP-5 實測過同主機家族「16/17 端點連續約 40 分鐘壞掉」。**建物壞掉是少了建物;底圖壞掉是整個地表變空白。**
3. 與 PRD「公開免登入、純臺灣開放資料」相容,但與 A/B 的「零執行期依賴」不相容。

**放棄的是**:照片級的真實感,以及「不需要任何分類規則就能讓地表看起來對」的省事。**若 owner 願意由 human 去取得 NLSC 的快取/再散布授權確認,C 的取捨會整個翻轉**(離線烘焙後它就沒有執行期依賴,而真實感是 A/B 給不了的)。**那是一個 human 決定,我不推進。**

### 8.4 風格取捨(這一段是判斷,不是量測)

**建物本來就是無貼圖的實體塊**(NLSC 3D Tiles),路面是 mesh,路樹路燈是 instance。**在這個場景裡,依用途著色的地表是風格一致的;照片級底圖反而會讓無貼圖的建物顯得突兀。** 這是設計判斷,不是我量出來的,列在這裡是因為票要求回答,**它不應該被當成證據使用**。

## 9. 未量測與做不到的事

**不用文件描述代替量測;以下每一項都是我沒做到的。**

> **round-2 增補的前兩項,是初版這份清單漏掉、而且各自決定一個結論句的假設。** 一份「未量測清單」漏掉最關鍵的兩個假設,比沒有清單更危險 —— 它讓讀者以為已經數過了。

0a. **道路廊帶寬度沒有權威來源,而它決定「真正空白」的大小。** FTP-31 指定的 class→寬度 config **尚不存在**;本報告的主體用北市實測路面 GIS(**只涵蓋 > 8 m 的道路**),巷弄部分用我選的 2.5/3.0/4.0 m 半寬。**那個半寬是我選的,不是量到的**,故所有相關數字以區間呈現(§7.2)。初版用單一的 8 m 預設值且不分等級,已撤回。

0b. **NLSC 的完整腳印聯集我沒有量。** §7.5 量的是 3 個 500 m 方格 + 60 個 tile 的抽樣,並以每棟凸包近似腳印;**整個 bbox 的 NLSC 腳印聯集未量測**。已知的是比值(NLSC/OSM 面積 1.18–1.42×)與方向(用 OSM 代理會低估 NLSC,故本報告的空白為高估)。

1. **我沒有用 Geofabrik 全臺 extract。** B 的數字來自 Overpass 的 bbox 查詢。兩者底層同源,但**我沒有實測兩者對同一 bbox 是否給出相同結果**。正式採用 B 前應以 extract 路徑複核一次。
2. **A 的 CRS 是推定的**(座標範圍),不是資料宣告的。檔內無 `.prj`。
3. **A 的 `顏色` 欄位我沒有解讀。** 它可能直接給出官方配色,對下游有用。
4. **河岸表現無法從 M1 判斷**(§4.5):bbox 內幾乎沒有水域。
5. **C 的可用性只涵蓋兩個各約 1–2 分鐘的窗**(§6.2),**量不到 FTP-5 觀察到的 40 分鐘故障型態**。
6. **我沒有渲染任何東西。** 本報告沒有一張圖是我看過的畫面;「看起來像什麼」全部是推理,不是觀察。
7. **我沒有量編譯進 tile 的成本**(檔案大小、產出時間)。那取決於尚未決定的 tile 格式。
8. **B 的類別重疊我沒有解決**,只揭露(§5.2)。跨類優先順序是 contracts 票要定的。
9. **`amenity`/`place` 的地表化白名單是我定的**(`parking`/`school`/`university`/`hospital`/`college`/`kindergarten`/`square`),**未經第三方確認**;換一組白名單覆蓋率會變。這是本報告覆蓋率數字裡最主觀的一個選擇。
10. **邊緣帶為何比內部更滿,成因未判定**(§2.4)。
11. **C 的「鋪滿地表」未經抽驗**:無資料磚同樣回傳合法 JPEG,而本報告沒有判讀過任何一張磚的影像內容(§6.4)。
12. **`_close` 的 0.05 m 環接合容差、`--min-hole` 的 100 m² 門檻**同樣是我選的常數。前者現由考卷以 5 m 缺口釘住方向,後者只影響洞的計數不影響覆蓋率,但兩者都不是量到的。

## 10. 授權(引用既有裁定,不重新論證)

### 10.1 B(OSM)— ODbL 1.0

依 [`LICENSING.md`](../../LICENSING.md)(FTP-6,已裁定):衍生 tiles **可公開散布**;OSM 衍生資料庫為 **ODbL Derivative Database**,義務為 share-alike、attribution(`© OpenStreetMap contributors`)、隨資料庫本體交付授權連結(**Databases safe harbour**,僅 HUD 標示不足)、免費提供機器可讀之全量衍生資料庫。FTP-29 已建立來源隔離目錄與 `ATTRIBUTION.md` 機制。

### 10.2 A(data.taipei)— OGDL v1

依同文件:data.taipei 來源適用[政府資料開放授權條款第 1 版](https://data.gov.tw/license),**顯名標示為失權要件**(未盡標示義務視為自始未取得授權)。改作、散布、再轉授權均在授權範圍內。

**本 spike 新增的一項提醒**(不是新裁定,是把既有裁定套到本題):FTP-6 對 props/physics 層下過「**不得引入 OSM 來源資料**」的工程約束,理由正是 share-alike 外溢。**地表著色層若採主案(A+B 合併),就是刻意讓一個含 OGDL 來源的圖層變成 ODbL Derivative Database。** 這在 road tiles 上已經是既定作法(FTP-6 表格第一列),但**地表層要不要比照,必須由 human 明確裁定**,不能由本 spike 推定。

### 10.3 C(NLSC)— `unverified`

FTP-6 明文**不對 NLSC 圖資授權作結論**;FTP-5 §1.3 認定服務條款**未規範**快取/代理/再散布,標記 `unverified`。→ **離線烘焙進散布物的授權依據目前不存在**(§6.3)。

## 11. 外部參照:hop.earth / three-geo(**二手,推論邊界寫在前面**)

**這一節不是資料,是一個參照。它沒有影響上面任何一個數字。**

**二手部分(我沒有第一手觀察)**:coordinator 轉述,`hop.earth` 這個站在做類似的可駕駛/可行走真實世界 3D 場景,其 `ATTRIBUTIONS.md` 列出 three.js + Bullet(Ammo.js)+ three-geo + Copernicus/IGN/CNIG 高程 + OpenStreetMap 向量 + LERC/Draco/ASTC 壓縮,而**該檔案中未見任何衛星或正射影像的授權標示**。

**推論邊界(必須連著讀)**:

1. **我沒有觀察過 hop.earth 的任何畫面,也沒有讀過那個 `ATTRIBUTIONS.md`。** 該站對 WebFetch/curl 回 403。**這一整段是轉述。**
2. **「授權清單裡沒有」不等於「沒有用」。**
3. **這一點我第一手查證了,而且它削弱上面的解讀**:`three-geo`([w3reality/three-geo](https://github.com/w3reality/three-geo),MIT)的 README 明載其地形建構**以 Mapbox Maps API 的衛星圖磚上貼圖**,且 `tokenMapbox` 「**must be provided**」;另一個模式 `getTerrainVector` 產出的是**等高線圖**(`dem-vec-shade-<ele>-`),**不是 landuse 著色**。
   → **這個函式庫的兩個模式都不是「OSM landuse 多邊形著色」**:一個是需要金鑰的商用衛星影像,一個是高程等高線。
4. 它是 three.js 架構,本專案是 Cesium(RFC D1)。**地表著色的資料源選擇與渲染引擎無關**,所以參照仍有效;但**本報告不對 D1 表示任何意見**(D1 的翻案觸發器是空場景 + NLSC 基礎開銷 > 6 ms,屬 FTP-48/49,尚未量測)。

**結論**:**這個參照不能當成「選項 B 的存在證明」。** 它證明的是「有人用 OSM 向量 + 國家級高程做出可用的場景」,但它所用的函式庫的預設地表著色是**商用衛星影像(需金鑰)**,那正是本專案的 PRD 排除的東西。**我未觀察到的東西,不能當成證據。**

**一個附帶有用的線索**(不在本 spike 的 Scope,交 contracts 票參考):該清單使用 **LERC**(高程柵格)、**Draco**(網格)、**ASTC**(貼圖)壓縮,是已被實務驗證的選擇,可作為 tile 格式票的量級參考。**格式定案不在本 spike。**

### 13.5 方法論教訓(本輪最該記住的一條)

**B1 的教訓不是「參數選錯」。** 量測方法是嚴謹的、幾何是正確的、算術是對的 —— 但**一個沒有來源的預設值被寫進結論句之後,就變成一個沒有人知道自己在相信的假設**。嚴謹的方法乘上一個猜測的輸入,產出的是一個**有小數點的猜測**,而小數點會讓它看起來像量測。

**判準**:凡是進入結論句的數字,其**每一個輸入**都必須能指名出處;指不出來的,就是未決前提,必須以區間呈現並列入 §9 —— 而不是讓預設值悄悄補上。

**B3 是同一個病的另一面**:「N/N killed」若不說明 N 是怎麼挑的,它描述的是我的選擇,不是程式的性質。
