## 2. 量測方法

### 2.1 共用同一套幾何程式

A 與 B **走完全相同的 union / clip / hole 程式碼**([`ground-probe.py`](ground-probe.py) 的 `coverage`、`holes`、`class_areas`、`edge_band`)。若兩邊各用各的幾何邏輯,比較出來的會是兩支 script 的差異而不是兩份資料的差異。

量測 CRS 一律 **EPSG:3826**(公尺),bbox 由 `contracts/constants/m1_area.json` 讀入,**不另存一份**(與 `etl/osm/bbox.py::from_area_file` 同一個來源)。

### 2.2 兩種獨立方法的對帳

headline 覆蓋率同時用**精確聯集**(shapely `unary_union` → `intersection` → `area`)與**網格取樣**(5 m 間距、cell 中心、490,000 個取樣點)量,兩者失敗方式不同,所以一致才有證據力。

| 資料源 | 精確聯集 | 網格取樣(5 m,490,000 點) | 差 |
|---|---|---|---|
| B(OSM) | 0.554774 | 0.554743 | **−3.1 × 10⁻⁵** |
| A(細計圖) | 0.777727 | 0.777712 | **−1.5 × 10⁻⁵** |

(probe 另外獨立輸出一個 `delta_vs_exact` 欄位,其值為 −1.4 × 10⁻⁵;差異來自它對差值自行四捨五入,而非上表兩個 6 位小數相減。以表內兩欄相減為準。)

再加一層:**同一份 OSM 輸入在兩個不同的 shapely 版本上跑出逐位元相同的結果**(venv shapely 2.1.2 與 anaconda shapely 2.1.1,皆為 `covered_m2 = 6795975.6`、`fraction = 0.554774`、9 個洞且面積清單完全相同)。這排除「數字是某個函式庫版本的產物」。

### 2.3 零值對照組

**本報告出現的每一個 0,都附一個用同一支函式、同一條路徑會回報非零的對照組。** 沒有對照組時,「0 個洞」跟「查詢寫錯了」長得一模一樣。

| 回報 0 的量測 | 對照組(必須非零) | 結果 |
|---|---|---|
| A 的 `holes` 在未排除範圍框時 = 0 | 排除範圍框後同一函式 = 2 個洞、2,722,819 m² | 對照組非零 ✓ |
| `skipped = 0`(兩個資料源皆然) | 考卷 `test_degenerate_rings_are_skipped_and_counted`:3 點環 → `skipped = 1` | 對照組非零 ✓ |
| 完全在 bbox 外的 polygon 貢獻 0 | 同一函式對跨界 polygon 回報 2,500 m²(考卷 `test_polygon_crossing_the_edge_counts_only_the_inside`) | 對照組非零 ✓ |
| 邊緣帶覆蓋 0(考卷合成案例) | 同一函式對滿覆蓋輸入回報 1.0 | 對照組非零 ✓ |
| **data.taipei `/api/v1/dataset/search` 回 `count: 0`** | **空查詢、`'a'`、`'公園'`、`'臺北'`、`'交通'`、`'土地'` 全部也回 0** | **對照組也是 0 → 這個端點無條件回 0,不能用它推論任何事**(見 §4.1) |

最後一列是這條紀律當場救到的一次:若沒有對照組,我會寫成「data.taipei 上找不到土地使用分區資料集」——**那是錯的**,資料集存在(§4.2)。

### 2.4 邊界(bbox 邊緣)有沒有空白帶?

**沒有。** 跨界 polygon 被裁切後,內側部分照算(考卷釘住)。但「有沒有算到」不等於「邊緣看起來有沒有變薄」,所以直接量**沿邊 50 m 帶**的覆蓋率與**內部**的覆蓋率:

| 資料源 | 邊緣帶(50 m)覆蓋 | 內部覆蓋 | 差 |
|---|---|---|---|
| B(OSM) | 58.48% | 55.30% | **+3.18 pp**(邊緣比內部更滿) |
| A(細計圖) | 77.63% | 77.78% | **−0.15 pp** |

兩者都沒有邊緣空白帶。B 的邊緣反而更滿,**成因未判定**——bbox 南緣外是象山山區,大面積 `natural=wood` 跨界進來是一個合理的解釋,但我沒有做能分辨其他解釋的量測,所以不下判定。

跨界元素計數:B 有 54 個 polygon 被裁切、62 個完全在外;A 有 123 個被裁切、13,803 個完全在外(A 是全市檔案,所以「在外」的很多)。

### 2.5 不回述上游 body 是被考卷釘住的

probe 的可用性取樣紀錄**只帶** `at` / `status` / `bytes` / `body_class` / `content_type` / `ms`,錯誤樣本只帶 `at` / `status` / `error_class` / `ms`。考卷用 **allow-list 釘住鍵集合**,不是搜尋某個已知字串:

> 早期版本的考卷只檢查「完整 body 沒有出現在輸出裡」,結果一個把 body 前 16 bytes 以 hex 塞進紀錄的 mutant **活了下來**(M13)。前 16 bytes 也是別人的 body。改成 allow-list 後該 mutant 被殺掉。

**exception 只記型別不記訊息**(`error_class = type(exc).__name__`)——訊息可能夾帶 body 內容。這條也有 mutant 證明過會紅(M6)。

### 7.3(round-3 更正)NLSC 建物覆蓋:我上一輪算錯了,而且錯在討喜的方向

round-2 我宣稱 NLSC 腳印是 OSM 的 **1.18–1.42 倍**,並據此寫「本報告的空白是高估、區間是保守的」。**兩個錯誤:**

1. **漏掉 y-up → z-up 旋轉。** 3D Tiles 規定 b3dm 內的 glTF 為 Y-up,套用 RTC_CENTER 前須先旋轉。我沒做,於是投影出來的是建物的**垂直切面**。
2. **凸包相加而非聯集。** footprint 覆蓋是**聯集**;把每棟(甚至每個 primitive)的凸包相加會重複計算 —— **這正是本報告考卷早已為 `class_areas` 釘住的 M12**。

> **我把一個在別處已經釘死的錯誤,原封不動地犯在新程式裡** —— 因為新程式沒有被納入那個 mutant 家族。這直接說明了 §2.6 的家族定義問題。

第一格的 65,044 m² 與 Layer 2 獨立實作的數字**逐位相符**。

**結論:比值落在 0.824–1.150,三格中有升有降,方向並未確立。** round-2 的「NLSC 比 OSM 密、所以空白是高估」**已撤回**;Layer 2 round-3 提出的「NLSC 比 OSM 疏、所以區間是下界」在我這三格裡**也不成立**(第二格 1.150)。**用一個相反方向的宣稱去取代原本的宣稱,會是第二個錯誤。**

### 7.5.1 關於「三輪都往同一個方向」——成因與它現在的極限

三輪更正都讓空白變大(9.73% → 15.9–22.6% → 17.1–27.2% → **16.2–27.5%**)。**這不是巧合,有真實成因:**

**每一個未經檢查的假設,先前都被解決成「已經有別的東西蓋掉它了」** —— 8 m 廊帶假設路面 mesh 蓋得很寬、道路用地假設整塊都是車道、OSM building 假設 NLSC 蓋得至少一樣多。**那是一個方向性的先驗**(傾向於相信空缺已被填補),所以每次檢查它都往同一邊修正。

**還有一個同向的、我漏掉的**:§9.9 說 `amenity`/`place` 的地表化白名單是我自訂的,並自稱是「覆蓋率數字裡最主觀的一個選擇」——**但它沒有進這份清單**。它同向:`amenity=school` 434,824 + `amenity=hospital` 76,714 + `amenity=university` 51,084 ≈ **562,622 m² ≈ 4.6 pp**,全部計入 B 的覆蓋。**收窄白名單 → 覆蓋變小 → 空白變大**,與上述三次是同一個先驗方向(「傾向相信空缺已被填補」)。**它沒有被傳播進 §7.5 的區間。**

**但剩下已識別的誤差不再指向同一方向:**

- **人行道以比例而非幾何扣除**:若人行道恰好較集中在已被 landuse 覆蓋處,現行修正會**高估**空白 → 往下。
- **車道欄位選擇**:若分隔島實際上會被路面 mesh 一併鋪掉,正確值是 19.78% 而非 28.92% → 往下。
- **NLSC 全域腳印聯集**:方向未定。

→ **這是三輪以來第一次出現向下的證據。** 因此本節不宣稱「還會更大」,只宣稱**在已具名的維度上有界**。

### 7.6 三塊拆解不是分割,而且不依賴減法順序

> 初版寫「19.0% 在建物腳印底下」,那是**先扣掉道路廊帶之後**的殘量,**照字面理解是錯的**。

`blank_split` 把**每一項都對「空缺」本身取交集**,並回報兩者的重疊(考卷 `test_blank_split_is_order_independent_and_names_the_overlap` 釘住,對應 mutant R7)。以「實測路面 + 可行駛 @ 3.0 m」、B(OSM)為例:

| 量 | 值 |
|---|---|
| 空缺(bbox − B 覆蓋) | 5,454,024.4 m² |
| 空缺 ∩ 道路廊帶 | 1,923,806.0 m² |

## 8. 建議:主案 + 備案 + 選它會放棄什麼

**這一題不由 agent 定案。以下是建議,裁決在 owner / RFC。**

> **關於 owner 對 B 的初步偏好:量測支持它,但不是無條件支持 —— 而且 round-2 之後,支持得更有保留。**
> B 的**分類語意**確實比 A 適合著色(`wood`/`park`/`grass` 直接對應外觀;`住3`/`商三特` 要多一層假設),粒度細 7.6 倍,無效幾何比率較低(0.46% vs 0.79%,約 1.7 倍,**不是一個數量級** —— 初版那句比較拿 bbox 內的 B 對上全市的 A,已更正),而且零新資料源。
> **但 B 單獨會留下 16.2%–27.5% 的地表沒有分類**(初版誤寫 9.73%,round-2 誤寫 15.9%–22.6%),而 A∪B 能把它壓到 **3.5%–9.0%**。**兩輪更正之後,補洞的邊際效益從 8.77 pp 變成 15–17 pp** —— 更正**強化**了混合方案,同時**削弱**了「B 單獨」這個備案。

### 主案:**B 為主分類 + A 補洞(皆離線編譯進 tile)**

1. 地表分類以 **OSM landuse/natural/leisure** 為準(粒度細、語意直接對應外觀)。
2. OSM 未覆蓋處,以 **data.taipei 都市計畫「細部計畫圖」** 補(**不要用主要計畫圖**,中位 8,809 m² 一個街廓一個顏色,太粗)。
3. 剩下的 **3.5%–9.0%**(最保守 9.0%)吃一個中性預設色;**車道**交給 FTP-33 的路面 mesh(**人行道與分隔島不是車道,仍需著色**,見 §7.2)。
4. **零執行期外部依賴、純開放資料。**

### 備案:**B 單獨**

同上但不接 A,**16.2%–27.5%** 的地表吃預設色。**適用情境**:若 owner 判斷「多接一個每年更新、CRS 未宣告、環方向不符規範的來源」不值得那 13–17 pp。**這個備案在三輪更正之後明顯變弱** —— 一成的地表吃預設色與四分之一的地表吃預設色,是不同性質的取捨。

### 8.1 選主案(B + A 混合)放棄了什麼

1. **授權變複雜,而且踩到一個 FTP-6 明文未裁定的前提。** 依 [`LICENSING.md`](../../LICENSING.md),把 OSM 資料併進某圖層會使該圖層成為 **ODbL Derivative Database**,share-alike 外溢(FTP-6 對 props/physics 層明文下過這條禁令)。合併後的地表層若視為單一資料庫,**整層落入 ODbL**,連帶把 OGDL v1 來源的內容一起帶進 share-alike 範圍;若想讓兩層各自保有授權,需要依賴 FTP-6 標為「**前提未裁定**」的 Collective Database 定位。**這是本主案最實質的代價,而且它是一個 human 決定,不是工程決定。**
2. **兩種更新節奏**:OSM 持續變動、A 每 1 年。兩者不同步時,補洞的邊界會跟著 OSM 漂移。
3. **A 的 ingestion 風險**:無 `.prj`(CRS 需向提供者確認,本報告只做推定)、99.2% 的 shape 環方向不符 ESRI 規範、CP950 編碼。
4. **語意混用**:同一張畫面上,一部分顏色代表「地表實際是什麼」,另一部分代表「這塊地被規劃成什麼」。**規劃用途可能與現況不符**(規劃為 `住3` 的地可能是工地),混合後**看起來會很有把握地畫錯**。這是我認為最容易被低估的一項。
5. 多一份 4 MB 來源要版本控管與標示。

### 8.2 選備案(B 單獨)放棄了什麼

1. **16.2%–27.5% 的地表(約 1.98–3.37 km²)沒有分類**,只能吃預設色。以 M1 的尺度,那是駕駛會持續看到的一大片,不是零星角落。(**面積為實測;「駕駛會看到」是推論,我沒有渲染過畫面**,見 §9.6。)
2. 放棄 A 對 B 的**交叉佐證**(§4.5 的 `公` vs `park`、`保` vs `wood`)。
3. **OSM 是活資料**:覆蓋率會隨編輯漂移,可能變好也可能變差,而沒有第二個來源兜底。

### 8.3 不採用 C 放棄了什麼

**先講清楚不採用的理由不是什麼:不是我量到它不可靠(48/48 全綠)。** 理由是:

1. **授權未裁定**(§6.3):要把影像烘進我們散布的 tile,目前沒有已確立的授權依據。而**不烘進 tile 就等於接受執行期外部依賴**。
2. **執行期外部依賴的後果不對稱**:FTP-5 實測過同主機家族「16/17 端點連續約 40 分鐘壞掉」。**建物壞掉是少了建物;底圖壞掉是整個地表變空白。**
3. 與 PRD「公開免登入、純臺灣開放資料」相容,但與 A/B 的「零執行期依賴」不相容。

**放棄的是**:照片級的真實感,以及「不需要任何分類規則就能讓地表看起來對」的省事。**若 owner 願意由 human 去取得 NLSC 的快取/再散布授權確認,C 的取捨會整個翻轉**(離線烘焙後它就沒有執行期依賴,而真實感是 A/B 給不了的)。**那是一個 human 決定,我不推進。**

### 8.4 風格取捨(這一段是判斷,不是量測)

**建物本來就是無貼圖的實體塊**(NLSC 3D Tiles),路面是 mesh,路樹路燈是 instance。**在這個場景裡,依用途著色的地表是風格一致的;照片級底圖反而會讓無貼圖的建物顯得突兀。** 這是設計判斷,不是我量出來的,列在這裡是因為票要求回答,**它不應該被當成證據使用**。

## 11. 外部參照:hop.earth / three-geo(**二手,推論邊界寫在前面**)

**這一節不是資料,是一個參照。它沒有影響上面任何一個數字。**

**二手部分(我沒有第一手觀察)**:coordinator 轉述,`hop.earth` 這個站在做類似的可駕駛/可行走真實世界 3D 場景,其 `ATTRIBUTIONS.md` 列出 three.js + Bullet(Ammo.js)+ three-geo + Copernicus/IGN/CNIG 高程 + OpenStreetMap 向量 + LERC/Draco/ASTC 壓縮,而**該檔案中未見任何衛星或正射影像的授權標示**。

**推論邊界(必須連著讀)**:

   → **這個函式庫的兩個模式都不是「OSM landuse 多邊形著色」**:一個是需要金鑰的商用衛星影像,一個是高程等高線。

### 13.5 方法論教訓(round-3 擴寫為一般形)

初版寫的是:**「一個沒有來源的預設值,一旦寫進結論句,就變成一個沒有人知道自己在相信的假設。」** 那句話是對的,但**它只涵蓋了我犯的那一版**。round-3 找到了同一個病的第二版,而且更難發現:

> **一個「有出處」的輸入,若它的**語意**沒有被對照你的用途檢查過,和一個沒有出處的預設值一樣危險 —— 而且更難發現,因為它有出處。**

**S7 就是這個形狀**:北市道路 GIS 有出處、有 `.prj`、有 checksum、是 RFC D10 指定的權威來源。**但它叫「道路用地」,不叫「車道」** —— 裡面 28.92% 是人行道、分隔島與側溝。我在同一份報告的前一節論證「FTP-33 不會鋪人行道」,下一節就把整塊多邊形算成已覆蓋。**出處的可信度,被誤當成語意的適用性。**

**因此判準有兩條,不是一條:**

1. **來源判準**:凡進入結論句的數字,其每一個輸入都必須能指名出處。指不出來的就是未決前提,以區間呈現並列入 §9。

### 17.1 B1 —— 修正本身讓失敗變得更可信(第五次,而且最利)

round-5 我加了 `building_input` 標籤來防止「缺建物輸入卻靜默出數字」。**但那個標籤讀的是 `--buildings` 有沒有出現在 argv,不是建物項有沒有進入計算。**

B 實測路面      36.19% – 37.14%   (完整 fetch:22.80% – 27.49%)
