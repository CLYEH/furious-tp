### 0.1 服務清單:同一 URL 交替回傳兩份不同的清單

**服務清單不是一份穩定的文件,引用它的數字時必須連同副本一起引用。** round-4 對 `https://3dtiles.nlsc.gov.tw/tiles3d/Service` 做 **12 次**序列取樣(2026-08-10 **17:56Z–18:08Z**;兩個交錯取樣窗共 11 次、窗間另有 1 次只讀 JSON 結構的單發請求;任兩次請求間隔 ≥6 秒,**0×429、0 錯誤**),取回**兩份不同的 body**,交替出現:

| 副本 | bytes | sha256(前 16 hex) | 本輪次數 | **總筆數** | `BUILDING` | `ROAD` | `ROAD2ND` | 地形(測試用) |
|---|---|---|---|---|---|---|---|---|
| **A** | 12,380 | `86fe007568c75ada` | 5 | **66** | 24 | 22 | **18** | 2 |
| **B** | 13,176 | `188c24930845b91b` | 7 | **70** | 24 | 22 | **22** | 2 |

兩份皆為 200、**未壓縮**、合法 JSON、`LAYERS` 結構相同。逐鍵的實際服務代碼:

| `LAYERS` 鍵 | 副本 A(12,380)| 副本 B(13,176)|
|---|---|---|
| `BUILDING` | 0–22、26(**24** 筆)| **與 A 逐筆相同** |
| `ROAD`(原始成果版) | 0–18、20、22、23(**22** 筆)| **與 A 逐筆相同** |
| `ROAD2ND`(地形貼合版) | 0、3–6、8–16、18、20、22、23(**18** 筆)| 0–18、20、22、23(**22** 筆;多出 A 沒有的 **1、2、7、17**)|
| 地形(測試用) | 2 筆(正射影像 / 電子地圖)| **與 A 逐筆相同** |

→ **兩份副本的差異只在 `ROAD2ND` 的四個代碼。`BUILDING` 在兩份中完全一致——都是 24 筆、都含代碼 22 與臺北市的兩筆條目。本報告的結論不依賴 `ROAD2ND`,因此不受這個差異影響。**

**成因未判定。** 從服務外部能確立的就是上表這件事本身:**同一 URL 回傳兩份不同 body**。是儲存副本、服務端組態、或其他什麼,**本輪沒有任何證據可以分辨,因此不下判定**(與 §3.4 同一紀律)。這件事對 D5 指紋的影響是實質的,已寫入 §5.1、§5.3 與 §6.3,不只是本節的註記。

> **round-4 更正 —— round-3 寫的「這是清點錯誤,不是資料漂移」已刪除,那句話是錯的。** 分開來說才對:
>
> - **初版數對了**:初版報告記錄自己取到的是 **13,176 bytes**(原文:「服務清單⋯(200,13,176 bytes,可正常解析)」),並列出「24 個建物圖層、22 個道路圖層(×2 版本)與 2 個試辦地形圖層」——那正是**副本 B** 的組成(24 + 22 + 22 + 2 = 70)。
> - **round-2 數錯了**:round-2 記錄自己取到的是 **12,380 bytes**(副本 A),卻寫成「共 70 筆⋯道路(地形貼合版)22」——那是副本 B 的數字。
> - round-3 的推論「本輪 body 與 round-2 那份 sha256 相同 ⇒ **不是**資料漂移」,只排除了**兩個剛好相同的樣本之間**的差異,推不到「這個 URL 只有一份 body」;而它自己同一節的括號註記裡,就記著當天量到的另一份 13,176。**這是連續第三輪在同一段落上把「我排除了 A」寫成「所以是 B」**(§12)。

其中**臺北市有兩筆建物圖層**(兩份副本皆然):

**初版報告只寫「清單另含 24 個建物圖層」便略過了第二筆,這是本報告初版結論錯誤的直接成因**(§10)。

### 1.2 商用許可 — **`unverified`**

**服務使用條款全文十點中,沒有任何一點提及商業/營利使用**,既未明文允許,也未明文禁止。平臺 FAQ 僅說明**無需申請**即可介接:

> Q:請問3D Tiles是什麼?該如何使用?

(取得方式:`SearchFromSQL?type=Quest&query=true`)

**「無需申請」是存取程序的敘述,不是授權範圍的授與。** 本專案為公開免登入服務,商用與否的界線需要肯定性授權依據,而條款未提供。

可查到的**肯定性**授權依據只有兩處,且**都不直接涵蓋線上 3D Tiles 服務的建物圖資**:

1. 平臺所採用的地形基礎是政府開放資料 —
   [data.gov.tw dataset 138563「2020年版全臺灣及部分離島20公尺網格數值地形模型DTM資料」](https://data.gov.tw/dataset/138563),
   該頁「授權方式」欄為**政府資料開放授權條款-第1版**、「計費方式」為**免費**、提供機關為地政司。
   OGDL v1 第二點(一)明文「**不限目的**⋯⋯進行利用」,即涵蓋商用([政府資料開放授權條款-第1版](https://data.gov.tw/license))。
   → 只證明**地形基礎**可商用,不及於建物模型。
2. 實體(離線)資料供應管道的授權說明(`tabidx=7`):
   > (五)其他事項 1.圖資授權之各項使用行為應適當以「顯名聲明」方式標示資料來源為內政部國土測繪中心。

   → 證明 NLSC 對三維圖資採「顯名聲明」型授權(與 OGDL v1 附件同一機制),但這是**公文離線申請**管道的條件,不是線上服務條款。

**結論:線上 3D Tiles 服務之商用許可,無法由一手來源確立,標記 `unverified`。** 若要公開發布商用/準商用產品,建議以正式函詢取得 NLSC 書面確認(見建議 R4)。

### 1.3 轉載 / 快取限制 — **條款未規範(`unverified`)**

服務使用條款**沒有任何條文**規範使用者端快取、代理(proxy)、鏡像或再散布 tile 內容。既無禁止,也無許可。與此相關的只有兩條間接條文:

- 第五點「本服務是不可移轉的(non-transferable)」— 文義指向**服務本身**(存取權)不得移轉,而非產出資料不得再散布;逐字解讀無法支撐「禁止快取」的結論。
- 第三點「本服務將會不斷更新,因此,您也可能需要配合適時適度修改您的網頁」— 隱含**要求跟隨最新版本**,對長期快取構成規範上的張力(快取愈久,愈偏離「不斷更新」的前提)。

**重要脈絡**:臺北市的三維建物模型是 NLSC **整合自臺北市既有成果**,而非 NLSC 自行產製:

> (108年度)2. 整合臺北市及桃園市完整區域與新北市及高雄市部分區域之既有三維建物模型(LOD1)。
> (109年度)2. 整合臺北市完整區域更新之既有三維建物模型(LOD1)。(`tabidx=3`)

因此在實體資料供應章節,NLSC 明文將臺北市排除:

> 資料範圍:全國(**臺北市不供應;請逕洽臺北市政府資訊局**)(`tabidx=7`,離線與線上申請兩處皆同)

→ NLSC **不以任何離線管道供應臺北市建物資料**,並將需求導向臺北市政府資訊局。任何「自行取得副本並自託管」的路線,對臺北市而言不能經由 NLSC 取得授權,必須另尋臺北市政府之來源與授權。此點同時解釋了 FTP-6 記錄的 [data.gov.tw 民眾需求 136485](https://data.gov.tw/suggests/136485) 之陳情內容。

## 2. AC2 — CORS 實測

**本 session 沒有 browser 工具,以下全部為 HTTP 層取得的一手 response header。**

### 2.1 preflight(`OPTIONS`)— 失敗(405)

```sh
curl -X OPTIONS -H "Origin: https://furious-tp.example" \
  -H "Access-Control-Request-Method: GET" \
  -H "Access-Control-Request-Headers: content-type" \
  https://3dtiles.nlsc.gov.tw/building/tiles3d/0/tileset.json
```

```text
HTTP/1.1 405 Method Not Allowed
allow: GET
access-control-allow-origin: *
access-control-allow-headers: *
access-control-allow-methods: *
access-control-allow-credentials: true
```

真實 tile payload 的 preflight 結果完全相同(405 + `allow: GET`)。

**判定**:依 Fetch 規範,preflight 必須回 ok-status(200–299)才算通過;405 **不通過**,即使帶了 `Access-Control-Allow-*`。→ **任何會觸發 preflight 的跨域請求都會被瀏覽器擋下**(自訂 header、非簡單方法等)。3D Tiles client 的預設請求是 simple GET,不觸發 preflight,故此限制在預設路徑上不致命,但**排除了任何需要自訂 header 的用法**。

### 2.2 實際 GET(帶 `Origin`)— 允許跨域

**可用端點(代碼 22)的 `tileset.json`**,round-2 實測:

```text
HTTP/1.1 200 OK
content-type: application/json; charset=utf-8
content-encoding: gzip
content-length: 3176361
cache-control: no-cache,no-store
x-aspnet-version: 4.0.30319
access-control-allow-origin: *
access-control-allow-credentials: true
```

**真實葉節點 tile**(`building/tiles3d/22/0_2_1_3_3_0_3_3_0_0_0.b3dm`,gzip 79,700 → 104,784 bytes,magic 驗證為 `b3dm`):

```text
HTTP/1.1 200 OK
content-type: text/html
content-encoding: gzip
content-length: 79700
cache-control: no-cache,no-store
access-control-allow-origin: *
access-control-allow-credentials: true
```

損毀端點(代碼 0)的 header 形狀相同,亦帶 `access-control-allow-origin: *` 與 `set-cookie: session-id=<uuid>`。

### 2.3 判定與界限

1. **跨域讀取本身成立**:`ACAO: *` 出現在 tileset 與真實 tile payload 的實際 GET 上,無 `Vary: Origin`。
2. **不得使用 credentials 模式**:`ACAO: *` 與 `access-control-allow-credentials: true` 併存;瀏覽器在 `credentials: "include"` 時會拒絕萬用字元來源。Cesium 預設不送 credentials → 可用,但 client 設定中**不得**開啟 `withCredentials`。
3. **不得觸發 preflight**(見 2.1)。
4. 服務對**每個** response 下 `set-cookie: session-id=...`(無 `SameSite`/`Secure`),跨站 subresource 情境下瀏覽器不會採用;對 client 無影響,但顯示服務端維持每請求 session 狀態。
5. **`.b3dm` 的 `content-type` 是 `text/html`(伺服器設定錯誤)**。CesiumJS 依 magic bytes 判讀 tile 內容,不受影響;但 FTP-39 若自行以 `content-type` 分派解析器會踩到。已知並記錄,非阻擋。

### 2.4 未執行事項(誠實揭露)

**我沒有在真實瀏覽器中載入過這個 tileset,也不宣稱做過。** 上述為 HTTP 層與 payload 結構層證據(magic / `byteLength` 自洽 / 內嵌 glTF offset 正確)。**「結構正確」不等於「CesiumJS 一定跑得起來」**,仍需補做:

- 於 Chrome DevTools 實際以 `fetch()`/CesiumJS 跨域載入代碼 22,確認無 console CORS 錯誤;
- 確認 §2.1 的 preflight 限制在 CesiumJS 實際請求路徑上未被觸發。

**指派建議**:併入 FTP-39 的第一項驗收(該票本就要求「信義 bbox 顯示 NLSC 建物」的截圖)。
**round-2 更正**:初版寫「在缺陷修復前這件事無法完成」——**該敘述已不成立**,代碼 22 的 tileset 今日即可解析,FTP-39 沒有技術前提待解。

### 3.4 缺陷分佈:實際觀察到的四個端點(**不作成因判定**)

初版斷言「缺陷精確落在 `3dtiles.nlsc.gov.tw` 上**被壓縮的 `tileset.json`**」;round-2 把它換成「缺陷是 **per-service-code**」。**兩個標籤都不成立**,理由見本節末的 round-3 更正。本節只陳述**量到的分佈**,不冠成因標籤。同主機、同為 gzip 的四個端點:

| 端點 | gzip | `content-length` | 結果 |
|---|---|---|---|
| `building/tiles3d/22/tileset.json` | 是 | 3,176,361 | **正常** → 16,068,240 bytes JSON |
| `building/tiles3d/0/tileset.json` | 是 | 2,775,617 | **損毀**(全 NUL) |
| `road/tiles3d/0/tileset.json` | 是 | 418,890 | **正常** → 1,987,274 bytes JSON(`asset.version 1.1`) |
| `road2nd/tiles3d/0/tileset.json` | 是 | 418,458 | **損毀**(~98% NUL,逐次變動) |

這張表**排除**得了幾個單一變數的解釋——每一項都是「這個變數無法預測誰壞」的否定式觀察,不是成因:

- **只看「宣告 gzip」不能預測**:四者皆宣告 gzip,兩者正常、兩者損毀。
- **只看檔案大小不能預測**:損毀的 `building/0`(2.78 MB)比正常的 `building/22`(3.18 MB)**還小**。最貼近的對照是最後兩列——`road/0` 與 `road2nd/0` 的 `content-length` **只差 432 bytes**(418,890 vs 418,458),同主機、同編碼、同內容型別,一個正常、一個損毀。
- **只看圖層類別不能預測**:建物與道路各自都同時存在正常與損毀的代碼。
- **只看服務代碼的數字也不能預測**:`road/tiles3d/0` **就是代碼 0,而且正常**;代碼 0 在 `building` 與 `road2nd` 損毀,在 `road` 正常。

**能說到這裡為止。** 這四項合起來只支持一句話:**在本輪量到的四個端點中,損毀與否無法由壓縮、大小、圖層類別或代碼數字單獨預測**。至於成因是逐份儲存副本、逐台後端、逐支產製流程還是別的什麼,**本輪沒有任何證據可以分辨,因此不下判定**。

兩個損毀端點的**樣態也不同**,如實記錄:`building/0` 是 100% NUL 且逐次穩定,`road2nd/0` 是 ~98% NUL 且逐次變動。**這件事本身不能用來推論成因**——它既相容於「多個獨立問題」,也相容於「單一機制、殘留內容隨當下記憶體內容而異」(§3.5 觀察到的正是後者的樣態)。

**這決定 R1 該向 NLSC 說什麼**:不要送出任何成因假說(「gzip 環節壞掉」「per-service-code」都是我們證不出來的),**只列舉觀察**——「`building/tiles3d/0` 與 `road2nd/tiles3d/0` 的回應無法解碼;**同主機**的 `building/tiles3d/22` 與 `road/tiles3d/0` 同日正常」。成因由有伺服器存取權的一方判斷,那是他們才做得到的事。

> **round-3 更正**:round-2 在同一張表下寫的結論句是「**缺陷是逐一服務代碼(逐份儲存副本)的個別現象**」。**這個標籤同樣不成立,已撤回** —— 表格自己就反證了它(`road/0` 是代碼 0 而且正常,所以「逐服務代碼」不是判準);而「兩個端點失效樣態不同 ⇒ 非單一系統性成因」是 non-sequitur,單一機制本來就會產生逐次不同的殘留內容。**連續兩輪在同一段落上用了兩個證不出來的成因標籤**,本輪改為只陳述觀察。

### 3.5 資安:損毀端點正在把**伺服器行程記憶體**回給匿名呼叫者

初版把 `road2nd/0` 的現象寫成「型態近似未初始化緩衝區」。**這個描述低估了嚴重度。** round-2 對回應中的非 NUL 殘留做了**分類分析(不保留、不轉載內容)**,結果:

| 觀察(取樣 A,單次回應) | 值 |
|---|---|
| 非 NUL 位元組 | 7,497 bytes,分佈於 1,155 個不連續區段,最長區段 257 bytes |
| Windows x64 使用者空間位址形狀的 8-byte word | 379 個 |
| X.509 OID 形狀字串(相異) | 6 個,含 **TWCA 的 policy OID 弧**、CA/Browser Forum 的 `2.23.140.1.2.2`、以及 X.509 EKU 弧 |
| UTF-16LE 可列印字串區段 | 1 段、31 字元(內容為 Windows 通道加密提供者名稱,屬作業系統常數) |
| ASCII 可列印區段 | 159 段 |

取樣 B(4 秒後)只剩 106 bytes 非 NUL、0 個 OID、0 段 UTF-16LE。**同一端點、同一長度,殘留量與內容逐次劇烈變動。**

綜合判讀:回應主體是一塊**被重複使用的行程記憶體**,其內容隨伺服器當下處理的工作而變。來源端為 IIS(`x-aspnet-version: 4.0.30319`),TLS 鏈為真實 TWCA 憑證(已驗,無中間人),故這些位元組**來自伺服器行程本身**,而非傳輸途中被竄改。

**這是資訊洩漏(information disclosure),不是單純的內容損毀**:

- 洩漏對象是**匿名、未認證**的任何人;
- 洩漏內容**逐次不同**,今日觀察到的是 TLS/憑證處理相關結構,但沒有任何機制保證下一次不是**其他使用者的請求資料**;
- 洩漏的位址類資訊會削弱 ASLR 的防護價值。

**處置原則(本報告已遵守)**:

- 本報告**不轉載任何殘留位元組的內容**,只描述類別與計數。轉載等同二次散布可能含他人資料的內容。
- 位址值一律不記錄。
- [`nlsc-probe.mjs`](nlsc-probe.mjs) 對回應主體只輸出長度、NUL 比例與 sha256,**從不輸出主體內容**;此性質已由 self-test 釘住(`response bodies are never echoed to stdout, only characterised`),避免日後修改把探測工具變成散布工具。
- 詳細技術特徵應於通報時**直接、私下**提供給 NLSC,不寫在公開 repo。

→ **R1 因此升級為資安通報,而非一般缺陷回報**(§7)。此事**不因代碼 22 可用而消失**:端點仍在對外洩漏記憶體。**發送通報是 human 的動作,本 session 不執行。**

## 4. AC3 — 限流 / 吞吐實測

### 4.1 量測倫理與 script 的內建克制

這是公開政府服務,且條款第九點允許機關隨時限流。[`nlsc-probe.mjs`](nlsc-probe.mjs) 因此把克制寫進程式,而非交給操作者自律:

- **序列請求**,無並行選項(`concurrency: 1`,自我測試以 fake server 的 `maxInFlight` 驗證);
- **硬上限 2 req/s**,`--rps` 超過即**夾住**(不是遵從),且夾住事實寫入輸出 `findings`;預設 1 req/s;
- **單一 429 立即中止**整輪(`abortReason: "rate_limited"`,exit 3),不重試、不硬闖,並記錄 `Retry-After`;
- 錯誤率超過 20%(且已達 5 次請求)即中止(`abortReason: "error_rate"`);
- `--max-requests` 預設 120,**涵蓋 tileset 探索與 tile 抓取兩階段**;
- 只沿路線 bounding volume 下降,**不遍歷整棵樹**(此性質亦已由 self-test 釘住);
- 不送 cookie/authorization(匿名存取正是受測的存取模式)。

### 5.3 建議機制(D5)

1. **指紋來源:解碼後的 `tileset.json` 全文 sha256**,而非 raw body。
   **理由(實測直接證得)**:損毀端點的 raw body 是全 NUL 且逐次穩定,對 raw bytes 取雜湊會得到「穩定」的假象——指紋會忠實地追蹤損毀內容。
   `nlsc-probe.mjs` 已據此區分 `rawSha256` 與 `decodedSha256`,且在無任何可解碼樣本時輸出 `bodyStableAcrossSamples: null`(不是 `true`)。
2. **輔助訊號**:tileset 頂層 `id`(代碼 22 = `112_A`)與 I3S 圖層的 `version` GUID。前者是成果批次識別,後者由**不同主機**供應;三者任一變動而其他未動,本身即值得告警。
3. **輪詢節奏**:每日一次(對照「更新頻率未定/2年」已極寬鬆),失敗採指數退避,**不得重試風暴**。
4. **告警條件(round-4 改寫:必須對「同一 URL 可能回不同 body」保持正確)**
   比對**不得**只保留「上一次的雜湊」,而應保留**看過的雜湊集合**(每個雜湊記首見/末見時間與出現次數)。據此分四類告警:
   - **改版**:出現新雜湊,且**連續 N 次輪詢只看到這個新雜湊**、舊雜湊不再出現(建議 N = 3,即三天)→ 才升為「tileset 改版」,觸發重新驗證流程(FTP-39/FTP-51)。**單獨一次看到新雜湊不得直接判為改版。**
   - **來源分歧**:新舊雜湊**交替出現** → 同一 URL 正在給出多份 body,這與改版**分屬不同告警**。服務清單今日就是這個樣態(§0.1);代碼 22 的 tileset 今日**未觀察到**,但規則必須先寫好——否則它第一次發生時,會被報成一次假的改版。
   - **服務缺陷**:無法解碼 → 與上述兩類都分開,否則缺陷會被誤報成改版。
   - **來源不一致**:`id` 或 I3S `version` 變動而雜湊未動(或反之)。三個訊號由不同主機/不同層供應,任一不一致都值得看,但**同樣適用上面的「連續 N 次」確認規則**。
5. **誤報風險 — 部分實測,整體仍 `unverified`(round-4 降級,round-2 的「已實測」撤回)**
   **量到的**:對 `building/tiles3d/22/tileset.json` 取樣 **11 次**,跨 **17:56:46Z–18:08:35Z(約 12 分鐘)**、間隔 ≥6 秒:`content-length` 全部 3,176,361、`rawSha256` 全部 `d5fce05313ce7e78`、gunzip 後全部 16,068,240 bytes、`decodedSha256` 全部 `17ef66b91c793f41`。**這 11 次取樣中,該 URL 沒有觀察到任何分歧。**
   **這不足以支撐「無須排除欄位」**:同主機的 `/tiles3d/Service` 在同一時段交替回兩份 body(§0.1),所以「同一 URL ⇒ 同一 body」在本主機上**不是**可以假設的性質。11 次取樣證明的是「**未觀察到**分歧」,不是「**不會**分歧」;round-2 依 3 次連續取樣寫下的「可直接對全文取雜湊,無須排除欄位」**已撤回**——3 次數秒內的取樣,分不出「內容穩定」與「連續拿到同一種回應」。
   **一項讓上面那 11 次更有份量的旁證,以及它的界限**:兩個 URL 的回應都可依「`Date` header 落後本機請求起始時間的幅度」分成兩群(**0.15–1.01 秒** / **4.19–4.92 秒**)。在服務清單上,這個分群與「拿到哪一份副本」**11/11 完全對應**——副本 A 的 5 次全落在 4.19–4.43 秒那群、副本 B 的 6 次全落在 0.34–1.01 秒那群(**第 12 次清單取樣來自一支只讀 JSON 結構的單發請求,未記錄該 header,故不計入**)。而 `building/22` 的 tileset **同樣出現這兩群**(11 次中 5 次落在 4.38–4.92 秒、6 次落在 0.15–0.82 秒),**11 次 body 仍全部逐位元相同**。→ 代碼 22 的一致性**不是只在單一種回應下量到的**。
   **但這兩個分群是否為同一件事,未確立。** `Date` 落後只是一個被觀察到的 header 現象,**其成因不判定**;它在清單上與副本身分相關,不代表它在 tileset 上也指向同一個區別。**不要拿它當任何判準**,本節也不以它推翻或支撐任何結論。
   注意:`set-cookie` 每次不同,但那在 header,不進入雜湊範圍。
6. **服務清單不得作為改版或下架訊號(round-4 新增)。** §6.3 風險 1 原本把「代碼 22 被下架」的偵測掛在監看服務清單上;**在清單的非決定性被釐清之前,它的長度與雜湊都不能當訊號**——它今日就會在 66 筆與 70 筆之間跳動,任何以「清單變了」為條件的告警都會穩定誤報。可用的替代做法,兩者都對本輪觀察成立:
   - **直接量目標端點**:請求 `building/tiles3d/22/tileset.json`,確認 **200 + 可 gunzip + `JSON.parse` 成功**。這是「代碼 22 還在不在」的直接答案,完全不經過清單。
   - **對清單做針對性斷言,而非整份比對**:斷言「`LAYERS.BUILDING` 仍含代碼 22 的條目」。本輪兩份副本的 `BUILDING` 逐筆相同,故此斷言對兩份都成立——但這是**今日的觀察,不是保證**。

## 6. 結論(三擇一)

> ### **直串可行(direct streaming)。不需要 caching proxy,不需要動態後端。**

### 6.1 推理

1. **官方端點今日可直串**:`https://3dtiles.nlsc.gov.tw/building/tiles3d/22/tileset.json` 回 200,gunzip 得 16,068,240 bytes 合法 3D Tiles JSON(85,209 節點),root sphere 涵蓋全部信義路線點;沿樹下降取得的真實葉節點 `.b3dm` 結構自洽、內嵌 glTF 正確,且全程 `access-control-allow-origin: *`(§3.1)。
2. **RFC 的「永久串官方 + 無動態後端」前提成立**,Plan B(caching proxy)**不需啟用**。
3. **損毀不是服務層級的失能**:同主機同日有正常端點(`building/22`、`road/0`)與損毀端點(`building/0`、`road2nd/0`)並存(§3.4;成因未判定,也不需要判定)。它對本專案的影響僅止於「臺北市建物要用代碼 22 這個端點」。
4. **授權面另有未決事項**:線上服務之**商用許可**與**快取/再散布**在條款中皆無規範(§1.2、§1.3),需 R4 的肯定性答覆才能支撐公開產品。**這與服務可行性是兩件事,不影響本結論。**
5. **另有一項獨立於本專案的資安事項**:損毀端點正在對匿名呼叫者洩漏伺服器行程記憶體(§3.5),應以資安通報處理(R1)。

### 12.3 考卷:`region` 案例補上單軸失效

### 12.4 方法論教訓(接續 §10、§11)

round-1 引用清單卻沒讀完;round-2 冠上「per-service-code」;round-3 冠上「清點錯誤,不是資料漂移」。**每一輪的修正動作本身,都造出了下一輪的 blocking**,而且**三次都是同一個動作**:手上只有觀察,卻交出了一個解釋。

所以本輪的規則寫死在這裡,給後續 spike 用:

- **陳述量到的,不陳述為什麼,除非能展示機制。**「同一 URL 回兩份不同 body」是觀察;「因為有兩台後端 / 有快取層 / 部署延遲」是我們從外部**證不出來**的解釋,連寫成「可能」都不寫——那只是把沒有證據的句子加上免責。
- **「成因未判定」是一項正確的發現,不是一個空格。** 它會改變下游的設計(§5.3 的告警規則正是因為成因未判定,才必須對兩種情形都保持正確)。
- **不能失敗的斷言不是證據**(§12.2 第 3 列),**只在一種情形下會失敗的斷言是半個證據**(§12.3 的單軸 mutant)。寫下「實測」兩個字之前,先問:**什麼樣的觀察會讓這句話變成假的?**
